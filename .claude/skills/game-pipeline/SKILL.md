# Game Pipeline — 개발 오케스트레이터

**실행 모드: 서브 에이전트 + 메인 직접 작업** (토큰 최적화를 위해 에이전트 팀 미사용)

## Phase 0: 컨텍스트 확인
1. `project-context` 스킬을 로드한다 (필수 — 코드베이스 탐색 금지)
2. 요청 유형 판별:
   - **신규 작업** → Phase 1로
   - **후속 수정** ("~만 고쳐줘", "보완해줘") → 대상 파일만 확인하고 Phase 2의 직접 처리로
   - **재실행/이어하기** → project-context의 파일 맵과 실제 파일을 대조해 중단 지점 파악

## Phase 1: 작업 분해
스펙을 구현 단위로 쪼갠다. 각 단위에 대해 Phase 2의 판단 기준을 적용한다.

## Phase 2: 직접 처리 vs 위임 판단 (토큰 절약 핵심)

| 조건 | 처리 |
|---|---|
| 파일 3개 이하 수정, 범위 명확 | **메인이 직접 처리** (에이전트 스폰 금지) |
| 독립적 대형 기능 (신규 화면, 신규 시스템) | `game-dev` 에이전트 위임 |
| 서로 독립인 대형 기능 2개 이상 | `game-dev` 병렬 스폰 (최대 2개) |

### UI 작업의 두 경로 — 무게를 맞춰라

UI 작업이라고 전부 풀 파이프라인(디자인 DB 조회 → 에이전트 위임 → CDP 실클릭 검증)을 돌리면
버튼 색 하나 바꾸는 데 20분이 든다. 규모로 갈라라.

| 경로 | 조건 | 절차 |
|---|---|---|
| **경량** | 파일 3개 이하 + 기존 토큰(`--sp-*`·`--fs-*`·`--el-*`·`--os-*`) 안에서 해결 + 새 시각 언어를 만들지 않음 (예: 간격 조정, 아이콘 교체, 문구 수정, 기존 색 재적용) | 메인이 직접 수정 → `npm run build` → **바뀐 지점만** 대비 스팟체크 → 끝 |
| **풀** | 새 화면·새 컴포넌트·시각 언어 변경(팔레트·타이포·스타일 방향) 또는 파일 4개 이상 | `ui-ux-pro-max` DB 조회 → 에이전트 위임 → CDP 실측 검증 |

⚠️ **기존 화면을 고치는 작업은 파일이 4개를 넘어도 풀 경로가 아니다.** 경로를 가르는 것은
파일 수가 아니라 **새 시각 언어를 만드는가**다. 버그 픽스·게임 규칙 변경·수치 조정은
파일을 몇 개 건드리든 디자인 DB도 CDP 실측도 필요 없다.

경량 경로에서도 **새 색·간격·그림자 값을 창작하는 것은 금지**다. 기존 토큰을 쓰거나, 토큰이
없으면 그 순간 풀 경로로 승격한다. 토큰을 새로 만드는 일 자체가 시각 언어 변경이기 때문이다.

위임 시 프롬프트 규칙:
- project-context 스킬 경로를 명시하고 "탐색 대신 이것을 읽어라"를 포함한다
- 스펙 + 대상 파일 경로를 프롬프트에 직접 담는다 (에이전트가 되묻지 않게)
- 코드 전문 반환 금지, 요약 반환을 요구한다
- **`ui-ux-pro-max` 로드 지시는 새 시각 언어를 만들 때만 넣는다**(새 화면·새 사이트·팔레트/타이포 변경).
  기존 화면을 고치는 작업에는 넣지 않고 "확정된 토큰만 쓰라"고 지시한다 — 그 스킬은 685줄이고
  DB 조회까지 딸려 와서, 색 하나 안 바뀌는 작업에 붙이면 그 값만큼 순수 낭비다.
  단 **토큰에 없는 값이 필요해지면 그 순간 새 시각 언어이므로 승격**한다는 조건을 함께 준다
- **검증 분량을 프롬프트에서 정한다**(기준은 Phase 3 표). 기본은 `npm test` + `npm run build`이고,
  실측은 `node scripts/measure.mjs`로 하라고 지시한다 — 에이전트가 CDP 배선을 새로 짜게 두지 않는다
- **테스트는 그 변경이 깨뜨릴 수 있는 것만** 덮게 한다. "규칙을 뒤집어 실패를 확인하라"는 증명은
  **돈·턴·게임오버를 만드는 불변식에만** 요구한다 — 그 외에는 회귀 테스트 하나로 충분하다

### 에이전트 모델 선택

**기본값은 세션 모델 상속이다 — `model` 파라미터를 생략하라.** 사용자가 `/model`로 고른 모델이
비용·속도 의도를 담고 있으므로, 그것을 임의로 덮어쓰면 사용자가 통제권을 잃는다.

| 작업 성격 | 모델 |
|---|---|
| 브리프에 코드·수치가 다 있고 옮겨 적기 + 검증이 주된 일 | 저렴한 티어 명시 가능 |
| 일반 구현·통합·디버깅 | **생략(상속)** |
| 아키텍처 판단, 시각 언어 설계, 전체 브랜치 리뷰 | `opus` 명시 |

턴 수가 토큰 단가보다 비싸다. 싼 모델이 3배 헤매면 결국 더 느리고 비싸므로,
애매하면 생략(상속)이 정답이다.

## Phase 3: 검증 — 변경의 성격에 맞춘다

| 변경 | 검증 |
|---|---|
| 데이터 수치·문구·CSS 조정 | `npm run build` |
| 기존 시스템 수정·버그 픽스 | `npm test` + `npm run build` + **그 변경이 깨뜨릴 수 있는 회귀 테스트 하나** |
| **새 시스템·새 상태 축**(타입을 늘려 data↔systems↔store↔UI를 함께 건드림) | 위 + `game-qa` 1회 |
| **새 화면** | 위 + `node scripts/measure.mjs --reduced --scan` |

⚠️ **`game-qa`를 기본으로 부르지 않는다.** 에이전트 하나가 project-context를 다시 읽고 파일을
다시 탐색하는 비용이, 이미 도는 테스트 800건이 잡아 줄 것을 한 번 더 확인하는 값보다 크다.
QA가 실제로 잡아 온 것은 **타입은 맞는데 뜻이 안 맞는** 종류(shape 불일치·상태 흐름 단절)뿐이므로,
**축이 새로 생기는 변경에만** 부른다. QA 이슈는 심각도 순으로 메인이 직접 고치거나 재위임한다.

⚠️ **실측(`measure.mjs`)도 새 화면에만 쓴다.** 배선을 다시 짜지 말 것 — 헤드리스의 함정
(얼어붙은 애니메이션 타임라인·어긋나는 좌표 클릭)이 전부 그 파일 주석에 있다.
**`--reduced` 없이는 CSS 애니메이션이 첫 프레임으로만 찍혀 거짓 결과가 나온다.**

## Phase 4: 마무리
1. 규칙이 바뀌었으면 `project-context`를 갱신한다 — 코어 `SKILL.md`(120줄 상한)가 아니라
   대개 `references/` 아래 해당 파일이다(shell·sites·systems·filemap·icons)
2. **사유는 소스 주석에만 쓴다.** CLAUDE.md 이력표는 한 줄, 커밋 메시지는 3줄 이내 — 같은
   판단을 세 벌로 쓰지 않는다(CLAUDE.md 사유 규칙)
3. `npm run build` + `npm test` 통과 확인 후 완료 보고

## 데이터 전달 프로토콜
- **반환값 기반** 기본. 에이전트는 요약만 반환 (산출물은 이미 파일에 있음)
- 대용량 중간 산출물이 필요한 경우에만 `docs/` 하위에 파일로 저장

## 에러 핸들링
- 에이전트 실패 시 1회 재위임. 재실패하면 메인이 직접 이어받아 처리하고 원인을 사용자에게 보고
- game-dev와 game-qa의 판단이 상충하면 삭제하지 말고 둘 다 사용자에게 병기 보고

## 테스트 시나리오
- **정상 흐름:** "상점 시스템 만들어줘" → Phase 0 컨텍스트 로드 → 대형 신규 기능이므로 game-dev 위임 → **새 상태 축이 생기므로** game-qa 1회 → `references/` 갱신 → 빌드+테스트
- **에러 흐름:** game-dev가 빌드 실패 반환 → 1회 재위임 → 재실패 → 메인이 에러 로그 직접 분석·수정 → 사용자에게 원인 보고
- **직접 처리 흐름:** "운동 활동의 체력 소모량 낮춰줘" → 데이터 파일 1개 수정이므로 스폰 없이 메인 직접 수정 → 빌드 확인 (QA 생략)
