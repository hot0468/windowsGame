## 2. 플레이어가 상시로 보는 것은 단 두 판

바탕화면에 항상 떠 있는 HUD는 `Desktop.tsx:356-357`의 둘뿐이다.

### CalendarPanel — 날짜를 **센다**
```
2026년 8월 14일
73일차 · 오후          ← 올라가기만 하고 목적지가 없다
맑음
[턴 넘기기] [자동 진행]
```
`{state.day}일차`는 **카운트업**이다. 카이로소프트의 "4년차 평가까지 D-120"이나 프메의 "성인식까지"와 결정적으로 다르다. 숫자가 커지는 것 자체는 아무 의미도 전달하지 않는다.

### StatPanel — 지금 값을 **비춘다**
15스탯 + 등급 뱃지 + 체력/멘탈/소지금. 랭크가 오르면 `fresh` 반짝임이 뜬다(`rankRose`).

**하지만 "다음 등급까지 얼마"가 없다.** `systems/rank.ts`에 `toNextRank`가 **이미 구현되어 있는데** StatPanel은 import만 하고(`StatPanel.tsx:8`) 화면에 안 쓴다. 필요한 계산이 이미 있는데 표시가 없는 상태다.

### 없는 것
- 목표 패널 없음
- 게임 시작 시 목적 제시 없음 (잠금화면 → 이름 입력 → 바로 바탕화면. `lockscreen/`에 안내 문구 자체가 없다)

## 3. 도감은 목표를 담고 있지만 아무도 안 연다

`ExcelApp.tsx`의 시트 4장(직업·엔딩·업적·관계)이 이 게임의 실질적 목표 화면이다. 코드 주석이 그 의도를 정확히 적어 뒀다:

> 업적은 **목표**다. 무엇을 하면 되는지 모르는 목표는 목표가 아니다. — `ExcelApp.tsx:288`

맞는 말이고, 그래서 업적 시트는 조건을 감추지 않고 `32 / 50` 형태로 진행도까지 보여 준다. **문제는 이 문장이 도감 안에서만 참이라는 것이다.**

도감으로 가는 길은 바탕화면 아이콘 하나뿐이다(`data/desktopIcons.ts`, `COLLECTION_KINDS`). 플레이어가 스스로 "저 엑셀 아이콘이 뭐지?" 하고 눌러 보기 전까지, 게임은 목표가 존재한다는 사실조차 알리지 않는다. **찾아가야만 보이는 목표는 동기가 되지 못한다** — 동기는 안 찾을 때도 눈에 들어와야 한다.

## 4. 가장 깊은 문제: 유일한 압력이 타이머다

확정 설계상 게임의 동력은 셋이다(project-context "날짜 제한" 항목):

1. 매일 생활비 차감 → 0이면 파산
2. 10일 주기 물가 인상
3. 번아웃 누적

**셋 다 벌이다.** 보상 축의 상시 압력이 하나도 없다. 결과가 이렇다:

| | 프메 | 카이로소프트 | 지금 이 게임 |
|---|---|---|---|
| 목표 제시 | 18세 성인식 = 처음부터 못 박힌 데드라인 | 4년 평가·랭크 승급 = HUD 상시 | **없음** |
| 진행 피드백 | 매년 평가 이벤트 | 매달 매출·순위 | 물가 인상 뉴스뿐 |
| 압력의 방향 | "그날까지 무엇이 될 것인가" | "다음 등급까지 얼마" | **"언제까지 안 죽나"** |

프메의 성인식은 **기대**다 — 그날 뭐가 될지 내가 고른다. 지금 88~101일은 **예고**다 — 그날 죽는다. 같은 "끝이 정해져 있음"인데 방향이 정반대다.

## 5. 구조적으로 조준 불가능한 엔딩 9종

`systems/ending.ts:55-60`:

```ts
if (reason === 'bankrupt') {
  const career = careerEnding(epitaphCareerId(state))
  if (career) return career
}
```

**직업 엔딩 9종은 파산해야만 뜬다.** 설계자 지시로 확정된 결정이고("직업엔딩은 취직한 순간이 아닌 돈 없어서 죽은 후 뜨게 해"), 비문(碑文)이라는 해석 자체는 일관된다. 다만 동기 구조 관점에서 대가가 있다:

- 전체 엔딩 15종 중 **9종이 "잘 해서 도달하는 것"이 아니라 "죽을 때 정산되는 것"**이다
- 실패 2종까지 더하면 **11 / 15가 파산·번아웃 경유**다
- 플레이 중에 조준할 수 있는 것은 **성취 4종뿐**이다:

| 엔딩 | 조건 | 조준 가능성 |
|---|---|---|
| 인플루언서 | 매력 80 | ○ |
| 철인 | 운동 200 | ○ |
| 현실주의자 | 소지금 180만 | ○ |
| 평범한 사람 | 지식 40 · 매력 40 | ○ (사실상 자동 도달) |

그리고 이 4종의 조건은 **엔딩 시트에서 감춰져 있다**(엔딩은 이야기의 끝이라 알면 김이 샌다는 규칙). 즉 **조준 가능한 목표 4개마저 조준경이 없다.**

## 6. 어디를 고치면 무엇이 풀리는지

비용이 낮은 순.

### A. `toNextRank`를 StatPanel에 표시 — 가장 싸고 즉효
이미 구현된 함수를 화면에 안 쓰고 있을 뿐이다. "지식 B까지 12" 한 줄이 스탯마다 붙으면 **매 턴 활동 선택에 조준점이 생긴다.** 파일 1~2개.

### B. 목표 HUD 패널 신설 — 도감을 바탕화면으로 끌어냄
가장 가까운 업적·가장 가까운 성취 엔딩·다음 랭크를 상시 노출. 데이터는 `achievementProgress`가 이미 계산한다. 새 패널이라 `HudPanel` 위에 얹으면 되고 확정 설계를 안 건드린다.

### C. 단기 목표 사슬 — 카톡/메일로 들어오는 과제
"이번 달 말까지 50만원", "자격증 하나" 같은 기한 있는 의뢰. `data/messages.ts`·`rankEvents.ts` 배선이 이미 있어 얹기 쉽다. **매 턴 "뭘 해야 하지"가 사라지는 효과가 가장 즉각적이다.**

### D. 데드라인 도입 — 구조 자체를 뒤집음
"D-100, 그날 당신은 무엇이 되어 있을 것인가"를 시작에 못 박고, 파산이 아니라 **결산일**이 끝이 된다. 직업 엔딩이 파산 조건에서 풀려 조준 가능한 목표가 된다.

⚠️ **확정 설계 두 개를 뒤집는다** — "날짜 제한 없음"과 "직업 엔딩은 파산 후". 밸런스 검증(`balance.verify.test.ts`)과 `ending.ts` 판정, 물가 외삽까지 연쇄로 흔든다. 효과는 가장 크지만 비용도 가장 크다.

## 판단이 필요한 지점

A·B·C는 서로 독립이고 확정 설계와 충돌하지 않는다 — 순서대로 얹어도 된다.
D는 **게임의 성격을 정하는 결정**이라 설계자 판단이 먼저다: 이 게임은 *생존물*인가, *육성물*인가.

지금 코드는 생존물인데, 질문("프메·카이로처럼 목표가 안 보인다")은 육성물을 기대하고 있다.
